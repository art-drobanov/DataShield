# DataShield Alpha-XVI — Руководство по декодеру

Справочник приёмной стороны: подача повреждённого текста или двоичного потока, сканирование, приём нескольких файлов, точки входа сборки, отчёты и управление состоянием.

## 1. Соглашения, используемые в документе

- **Пакет** — атомарная единица в 75 байтов, на проводе — 100 символов Base64 ([AlgorithmGuide §4](AlgorithmGuide.ru.md)).
- `H5` — 24-байтовый хеш заголовка; сид всех проверок секторов этого файла.
- **Слот** — состояние приёма на заголовок (версии, коллизии, счётчики); **сборка** превращает слот в байты файла.
- «txt-вход» — произвольный текст с Base64-материалом; «двоичный вход» — сырые 75-байтовые пакеты подряд.
- Значения прогресса живут на глобальной шкале 0..100; имена фаз — из `CodecStrings` (по умолчанию английский, русский — через `CodecStrings.Language = CodecLanguage.Russian`).
- `N`, `M`, `T = N + M` — число data-томов, ECC-томов и всего томов.

## 2. Конвейер декодирования одним взглядом

Декодирование — цепочка вытягиваемых, событийно выдающих стадий:

```text
источник (байты)  →  [только txt] фильтр Base64  →  сканер скользящего окна  →  накопитель приёма  →  слоты
```

| Стадия | Класс | Что делает |
|---|---|---|
| Источник | `ByteArraySource`, `StreamSource`, `FileSource` (`DataShield.Codec.IO`) | Качает байты в фоновой задаче; выдаёт порции размера буфера через `DataReady`. |
| Фильтр | `ByteRangeFilter` (`DataShield.Codec.StreamFilter`) | Только txt-режим: отбрасывает всё вне алфавита Base64. |
| Сканер | `SlidingWindowScanner` (`DataShield.Codec.StreamScanner`) | Скользит окном (100 Base64-символов или 75 сырых байтов) побайтово; выдаёт проверенные пакеты. |
| Накопитель | `StreamProcessor` (`DataShield.Codec.StreamProcessor`) | Классифицирует пакеты (заголовок / сигнатура / сектор), наполняет слоты. |
| Сборка | `ReceptionSlot.TryAssemble` | Восстанавливает файлы — предмет [AssemblyGuide](AssemblyGuide.ru.md). |

Всё, что декодер держит между вызовами `Scan` (хвосты сканеров, слоты), — данные пользователя: они вайпятся `Clear()` и `Dispose()`.

## 3. Быстрый старт

Накопительный приём основным классом:

```csharp
using var decoder = new StreamDecoder();

decoder.Scan(File.ReadLines("mangled_chat_export.txt"));   // накапливаем…
decoder.Scan(moreLines);                                    // …между вызовами

foreach (var slot in decoder.Slots)                         // по слоту на различающийся заголовок
{
    try
    {
        var content = decoder.TryAssemble(slot.Header);
        if (content is not null)
            File.WriteAllBytes(slot.Header.FileName, content);
    }
    catch (SignatureVerificationException)
    {
        // Exact(SHA-256) пройден, но ни одна принятая сигнатура не подтверждает — см. §10
    }
}
```

Одноходовое декодирование через фасад:

```csharp
using var codec = new DataShieldCodec(signaturePackets512: true);

byte[]? single = codec.Decode(
    File.OpenRead("stream.DataShield.bin"), OutputFormat.Binary);

List<DecodeResult> all = codec.DecodeAll(
    File.OpenRead("stream.DataShield.txt"), OutputFormat.Base64);

PacketIO.ScanFile(decoder, "stream.DataShield.txt");  // формат определяется по расширению
```

## 4. Создание декодера

```csharp
public StreamDecoder(
    SectorVersionSearchOptions? searchOptions = null,
    SectorScheme sectorScheme = SectorScheme.Classic,
    int virtualIndexSectorLimit = VirtualIndexHasher.DefaultSectorLimit,
    SignatureMode signatureMode = SignatureMode.Auto,
    string? hashSecret = null)
```

| Параметр | Дефолт | Значение |
|---|---|---|
| `searchOptions` | `SectorVersionSearchOptions.Default` | Лимиты поисков сборки (версии, подмножества) — каталогизированы в [AssemblyGuide](AssemblyGuide.ru.md). |
| `sectorScheme` | `Classic` | `Classic` — приём только классических пакетов-секторов. `VirtualIndex` — гибридный приём: классические секторы проверяются первыми, затем перебирается виртуальный индекс; файлы обеих схем читаются одновременно. |
| `virtualIndexSectorLimit` | `512` | Слоты с `T` выше порога проверяются только классически (перебор был бы слишком широким и слишком слабым — см. [CollisionBench](CollisionBench.ru.md)). Диапазон 1..512. |
| `signatureMode` | `Auto` | `Base` — детект сигнатурных пакетов без влияния; `Auto` — расширенная проверка активируется при приёме ≥ 1 сигнатурного пакета; `Force` — всегда активна (тогда отсутствие сигнатур проваливает сборку). |
| `hashSecret` | `null` | Область секретного хеширования на всю операцию; должен совпадать с секретом кодировщика, иначе заголовки просто не опознаются. Пустая строка = без секрета. |

Базовый класс `StreamCodec` валидирует схему и диапазон порога и делит с наследниками бесприцельный `RsCodecAdapter` (RS-матрица строится на каждый вызов, поэтому экземпляр безопасен при параллельном использовании — операции самого декодера сериализуются внутренней блокировкой).

Перед каждой операцией декодер гонит самотест хеширования (`Sha256Secure.Test()`, `Sha512Secure.Test()`) и отказывается работать при провале — повреждённая криптосреда не должна молча выносить неверные вердикты.

## 5. Форматы входа и перегрузки `Scan`

`Scan` **накопительный**: каждый вызов добавляет к слотам и хвостам сканеров, ничего не сбрасывая. Декодер различает:

| Перегрузка | Вход | Минимальная длина | Конвейер |
|---|---|---|---|
| `Scan(IEnumerable<string> lines)` | произвольные текстовые строки | суммарно 100 Base64-символов | UTF-8 конкатенация → фильтр → txt-сканер |
| `Scan(byte[] data)` | сырые байты пакетов (шум/рассинхрон допустимы) | 75 байтов | двоичный сканер, без фильтра |
| `Scan(Stream input, OutputFormat format)` | поток любого формата | — | формат задаёт txt или двоичный; позиционируемые потоки сообщают длину для прогресса |
| `PacketIO.ScanFile(decoder, path)` | файл | — | формат по расширению: `.txt` → Base64, `.bin` → Binary |

Замечания:

- Входы короче одного пакета молча игнорируются (сканировать нечего).
- Поток `Scan` не закрывает; он принадлежит вызывающему.
- Вызовы сериализуются: идущий `Scan` блокирует другие операции экземпляра.

## 6. Коммуникации: источники, обработчики, контракт выдачи

Все стадии реализуют `IDataSource`/`IDataProcessor` из `DataShield.Interfaces`:

- **Источник** качает байты в фоновой задаче в фиксированный буфер; при заполнении (или на EOF/остановке) выбрасывает `DataReady`, вручая потребителю одноразовый делегат вычитки; чтение возобновляется после возврата обработчика. Ошибки чтения сохраняются и всплывают через `Completion` (и свойство `Error`) — конвейер падает громко, никогда не молча.
- **Обработчик** подключается к вышестоящему источнику, преобразует каждый кусок под своей блокировкой и переиздаёт данные дальше через собственный выходной буфер. `Complete()` сбрасывает хвост — декодер вызывает его строго по порядку цепочки в конце каждого `Scan` (фильтр → сканер → накопитель), ибо финальный сброс и запускает позднюю перепривязку (§9).
- Выдача имеет два режима: байтовый (`Emit`) и **пакетный** (`EmitPacket`) — пакеты никогда не разрезаются границами выдачи; партия пакетов передаётся, когда их суммарный объём достигает размера буфера.

## 7. Фильтр Base64 (txt-режим)

`ByteRangeFilter.CreateBase64()` строит 256-элементную карту допустимости из пяти диапазонов: `A–Z`, `a–z`, `0–9`, `+`, `/`. Всё остальное — переводы строк, пробелы, кавычки, эмодзи, декорации «-----BEGIN-----» и символы паддинга `=` — отбрасывается до сканирования. Выживший поток — чистый Base64-материал, и сканер ищет в нём 100-символьные окна, декодирующиеся ровно в 75 байтов.

В двоичном режиме фильтр из цепочки исключён целиком.

## 8. Сканер скользящего окна

`SlidingWindowScanner` — толерантное к повреждениям ядро приёма. Он владеет:

- **окном** фиксированного размера (100 для txt, 75 для двоичного);
- **удержанным потоком** — каждым пропущенным через него байтом (именно это делает возможной позднюю перепривязку);
- `_scanPos` — насколько прямой проход потребил данные.

Прямой проход работает по позициям:

1. копирует окно из удержанного потока с позиции `_scanPos`;
2. вызывает обработчик (§8.1);
3. при распознавании выдаёт пакет и прыгает на продвижение обработчика (обычно размер окна); иначе сдвигается **на один байт**.

Побайтовый сдвиг и переживает обрезания, удаления и вставленный мусор: любой неповреждённый пакет в любом месте потока найдётся вне зависимости от выравнивания. Прыжок при успехе — эвристическое ускорение: на повреждённом потоке он может перепрыгнуть начало пакета, перекрывающегося с распознанным, — ровно поэтому существует исчерпывающий повторный проход (§8.2).

### 8.1 Контракт обработчика окна

```csharp
public delegate int WindowHandler(ReadOnlySpan<byte> window, out byte[]? emitted);
```

Возвращает продвижение потока в байтах (≥ 1) и, при распознавании, копию пакета. Окно действительно только внутри вызова. Обработчики декодера:

| Обработчик | Окно | Логика | Продвижение |
|---|---|---|---|
| `TxtWindow` | 100 символов | декодировать в 75 байтов (`Convert.TryFromBase64Chars`, ровно 75 записано), затем `_processor.Recognizes` | 100 при успехе, иначе 1 |
| `BinWindow` | 75 байтов | `_processor.Recognizes` напрямую | 75 при успехе, иначе 1 |

`Recognizes` принимает пакет, когда тот проходит автономную проверку (заголовок по `H5`, сигнатура по `S2`) или совпадает с сектором хотя бы одного существующего слота (классика: диапазон + хеш; VirtualIndex: перебор). Окончательная классификация — копия заголовка, сигнатура, чей слот получает сектор — дело накопителя (§10).

### 8.2 Повторное сканирование: исчерпывающая страховка

`RequestRescan(handler)` гонит **второй, исчерпывающий проход** по региону, который прямой проход уже посетил, — окно проверяется на *каждой* позиции, без прыжков. Корректность держат два правила:

- **Граница** — пройденный объём на момент запроса (все посещённые окна, включая выступ последнего), а не позиция выдачи: окна дальше прямого прохода он посетит сам — уже с новым знанием.
- Запрос, пришедший среди сканирования, **ставится в очередь** и выполняется по завершении текущего прохода; запрос простаивающему сканеру выполняется немедленно.

Переиздание уже принятого пакета безвредно по построению: слот лишь нарастит счётчик подтверждений (§10), версия никогда не дублируется.

## 9. Опоздавшие заголовки: адресная перепривязка

Сектор может быть отсканирован *раньше* своего заголовка (перемешанный поток, заголовки в конце). Сканер не смог классифицировать его тогда — `H5` ещё не существовало. Конвейер закрывает дыру удержанным потоком:

1. Накопитель принимает **новый** заголовок и поднимает `HeaderAccepted(header, headerHash)`.
2. Декодер запрашивает повторное сканирование на **обоих** сканерах (txt и двоичном) с обработчиком `RebindWindow`, привязанным к новому `H5` и `T`.
3. `RebindWindow` декодирует (txt) или копирует (двоичный) окно и принимает пакет, если тот — **классический сектор именно этого заголовка** (индекс в диапазоне + хеш `D3` под новым `H5`) либо — при включённой схеме VirtualIndex и `T` в пределах порога — сектор с виртуальным индексом (перебор от нуля: удержанные данные идут в порядке потока).
4. Если перепривязка адресована сканеру *другого* формата (заголовок пришёл в txt-`Scan`, а данные удержаны двоичным сканером), накопитель на время перепривязки подключается к тому сканеру, а затем возвращается к активному; двоичные и txt-вызовы `Scan` на одном декодере никогда не идут параллельно.

Повторный проход проверяет секторы только против *этого* заголовка, подтверждения остальных слотов не затрагиваются. Отсюда же требование к потребителям, рассчитывающим на полноту: финальный `Complete()` цепочки обязан отработать — декодер делает это в конце каждого `Scan`.

## 10. Граница накопителя приёма

`StreamProcessor` (подробно — в [AssemblyGuide](AssemblyGuide.ru.md)) — место, куда пакеты ложатся:

- **Пакеты-заголовки** — автономная проверка `H5`; побитно идентичное содержимое наращивает счётчик копий слота; новое содержимое создаёт слот (и стреляет `HeaderAccepted`).
- **Сигнатурные пакеты** — автономная проверка `S2`; копии считаются всегда; уникальные `S1` собираются в режимах `Auto`/`Force`.
- **Пакеты-секторы** — предлагаются каждому слоту; `H5` каждого слота решает принадлежность, что и не даёт файлам одного потока смешиваться.

Декодер экспонирует состояние только для чтения: `Slots`, `FileCount`, `SignatureMode`, `SignaturePacketCount`, `SignatureCheckActive`, `AcceptedSignatures` и наблюдаемые слота (карта валидности, карта коллизий, покрытие — см. §13).

## 11. Сборка файлов

`StreamDecoder.TryAssemble(HeaderContent)` сериализует заголовок, побайтово находит слот и делегирует сборке слота с RS-адаптером декодера, прогрессом, токеном отмены и — при активной расширенной проверке — собранными уникальными сигнатурами:

| Исход | Значение |
|---|---|
| не-`null` байты | Файл восстановлен и верифицирован (Exact SHA-256, плюс Any SHA-512 при активной проверке). |
| `null` | Повреждения превысили избыточность или лимиты. |
| `SignatureVerificationException` | Найден контент, точный по SHA-256, но ни одна принятая сигнатура его не подтверждает — тревога целостности, а не неудача декодирования ([AssemblyGuide §13.3](AssemblyGuide.ru.md)). |

Фасад оборачивает это удобно:

| Операция фасада | Поведение |
|---|---|
| `Scan` / `ScanText` | Накопительная подача (без сброса). |
| `Decode(stream, format)` / `DecodeText(lines)` | Один ход: сброс, скан, возврат содержимого первого файла (или `null`). |
| `DecodeAll(stream, format)` / `DecodeAll(progress, ct)` | Соответственно один ход / накопительно; возвращает `List<DecodeResult>`. |
| `DecodeResult` | `(ReceptionSlot Slot, byte[]? Content)` — полные детали приёма плюс содержимое либо `null`. |

Слоты собираются по убыванию `ReceivedSectorCount` (лучше покрытый файл — первым), поэтому «первый» у `Decode` — самый полный кандидат.

## 12. Прогресс, отмена, ошибки

- **Фазы.** До первого заголовка: «Поиск заголовков»; после: «Поиск секторов»; в конце: «Готово» (100 %). Фазы сборки (RS-восстановление, полный перебор, прокрутка, подбор подмножеств, «Сборка завершена») идут от слота и делят ту же шкалу 0..100.
- **Процент.** Доля потреблённых байтов источника (события `ConsumedAdvanced` сканера к общей длине, когда она известна — позиционируемые потоки и массивы; иначе фазовые сообщения без процента).
- **Отмена.** Токен проверяется на входе в `Scan`, в каждом колбэке прогресса, при ожидании конвейера (`Completion.Wait(ct)`) и на всём протяжении сборки. Отмена не трогает уже принятого — последующий `Scan` может продолжить тот же поток.
- **Ошибки.** Сбои ввода-вывода источника проваливают `Completion` (наблюдаются как исключения из `Scan`); свойство `Error` несёт причину.

## 13. Отчёты

`CodecReport` пишет человекочитаемый `.report.txt` рядом с выходом (путь = выход + «.report.txt»), локализуясь через `CodecStrings.Language`. Отчёт декодирования показывает сводку (имя, размер, SHA-256 — пересчитанный по собранному содержимому, когда оно есть, — счётчики заголовков/сигнатур, `N`/`M`, всего/принято/пропущено, покрытие) и построчную карту валидности, 64 сектора на строку:

```text
         ════════════════════════════════════════════════════════════════
         DataShield : Отчет по декодированию
         ════════════════════════════════════════════════════════════════
         Имя файла : REPORT.BIN
         Размер    : 640 байт
         SHA-256   : 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
         Заголовков: 3
         Сигнатурных: 3
         N (data)  : 10
         M (ECC)   : 1
         Всего     : 11
         Принято   : 10
         Пропущено : 1
         Покрытие  : 90.91%
         ────────────────────────────────────────────────────────────────
         Легенда: '█' — целостный, '▓' — коллизия, '░' — битый/отсутствует
         ────────────────────────────────────────────────────────────────

      0 │█████░█████──────────────────────────────────────────────────│ 10/11
```

Детали, которые стоит знать:

- При активной расширенной проверке и собранном содержимом SHA-512 печатается двумя выровненными строками под SHA-256.
- В режиме «с секретом» значения хешей «на проводе» защищены и непригодны к показу: отчёт пересчитывает реальные хеши по собранному содержимому в ОЗУ; где доступно только проводное значение (сборка не удалась), строка помечается концевой «*».
- `CodecReport.WriteSha256Sidecar(path)` пишет совместимый с `sha256sum` сайдкар `<поток>.sha256` рядом с восстановленным файлом потока.

## 14. Состояние, потокобезопасность, гигиена

| Аспект | Поведение |
|---|---|
| Параллельность | Все операции декодера сериализуются внутренним гейтом; RS-адаптер бесприценен и изначально безопасен параллельно. |
| Удержание | Сканер удерживает **весь** поданный поток (это нужно перепривязке); накопитель — принятые пакеты. Закладывайте `O(поток)` памяти на приём. |
| `Clear()` | Вайп слотов и хвостов сканеров; декодер сохраняет конфигурацию и готов принимать снова. |
| `Dispose()` | Отключает конвейер, вайпает всё; дальнейшие операции бросают `ObjectDisposedException`. |
| Самотест | Реализации SHA-256/SHA-512 верифицируются перед каждой операцией. |

## 15. Модель стоимости

| Операция | Стоимость |
|---|---|
| Проход фильтра | O(n) тестов байта |
| txt-скан, мусорный регион | одна попытка декода Base64 на позицию байта (декод ломается быстро на не-алфавите — на практике фильтр его уже снял, так что неудачи — это в основном промахи выравнивания) |
| txt-скан, валидный пакет | 1 декод + хеши классификации, прыжок 100 |
| Двоичный скан | хеши классификации на позицию; прыжок 75 при попадании |
| Повторное сканирование на новый заголовок | один исчерпывающий проход по пройденному объёму (классика: 1 хеш на окно; VirtualIndex: стоимость перебора на окно) |
| Удержанная память | один байт на байт входа, на каждый использованный сканер |
| Сборка | см. таблицу стоимости в [AssemblyGuide](AssemblyGuide.ru.md) |
