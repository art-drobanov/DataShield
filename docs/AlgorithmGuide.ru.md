## 1. Соглашения, используемые в документе

- **Диапазон байтов** `a..b` — включительно: байты со смещениями от `a` до `b`, то есть `b − a + 1` байт.
- `X ‖ Y` — конкатенация байтовых строк: сначала байты `X`, затем байты `Y`.
- `TruncN(X)` — **первые N байт** более длинного хеша. Все базовые хеши вычисляются полностью; усекается только представление «на проводе».
- Многобайтовые целые «на проводе» — **little-endian (LE)**, если не указано иное.
- `SHA-256(data)` и `SHA-512(data)` — стандартные алгоритмы. Там, где задан секрет хеширования, фактический расчёт выполняется *ключевым* вариантом из [§6](#6-система-хеширования); до этого читайте их как обычные хеши.
- Размеры: `B` = байты, `MiB` = 1 048 576 байт.
- «2⁻ⁿ» — вероятность, что случайное значение пройдёт n-битовую проверку.

## 2. Решаемая задача

DataShield передаёт **файл** через канал, которым он не управляет. Типичные каналы: сообщение в чате, вставленная заметка, тело письма, комментарий в тикете. Такие каналы регулярно:

- **обрезают** текст (лимиты длины сообщения, ручное копирование «главного»);
- **теряют фрагменты** из середины (сбои при копировании, ошибки в редакторе);
- **дублируют** фрагменты (цитаты при пересылке, повторные вставки);
- **перемешивают** фрагменты (ручная пересборка человеком);
- **впрыскивают посторонний текст** вокруг и между полезными частями (приветствия, подписи, чужие сообщения);
- **портят** короткие куски (автозамена, ошибки кодировки).

Инструмент на принимающей стороне получает произвольный ворох текста и обязан восстановить файл — бит-в-бит — из того, что уцелело.

Требуются два свойства:

1. **Живучесть.** Потеря контролируемой доли передачи не должна терять файл.
2. **Целостность.** Приёмник должен уметь *доказать*, что восстановленные байты — в точности исходные, включая случай, когда в кучу смешались куски двух разных передач.

Чего формат сознательно **не** обеспечивает:

> [!IMPORTANT]
> **Это не шифрование.** Полезная нагрузка передаётся открытыми байтами (упакованными в текст). Секрет хеширования (§6) делает подделку пакетов вычислительно недостижимой для сторон без секрета, но прочитать содержимое может кто угодно. Если нужна конфиденциальность — зашифруйте файл до кодирования; DataShield добросовестно перенесёт шифротекст.

## 3. Принципы проектирования

Формат собран из небольшого числа решений, применённых последовательно:

1. **Одна самодостаточная единица: пакет.** Файл нарезается на фиксированные 75-байтные пакеты, каждый превращается ровно в 100 символов Base64. Пакет либо цел и проверяем, либо мусор; «частично полезных» пакетов не бывает. Это упрощает задачу канала до предела: всё, что доставляет целые 100-символьные фрагменты, доставляет пригодные данные.
2. **Три независимых слоя избыточности.**
   - *Дублирование метаданных*: несколько копий пакета-заголовка и (опционально) сигнатурного пакета распределены по потоку, поэтому знание того, *что* восстанавливать, не зависит от одного фрагмента.
   - *Кодирование стираний*: чётность Рида—Соломона восстанавливает контролируемую долю потерянных пакетов с полезной нагрузкой (§9).
   - *Криптографическая привязка*: каждый пакет привязан к своему файлу усечённым хешем с сидом из хеша заголовка файла, поэтому фрагменты разных файлов не могут незаметно смешаться (§5, §6).
3. **Проверка раньше доверия.** Ни один пакет не принимается по одному синтаксису. Заголовок обязан проходить внутреннюю 192-битовую проверку; сектор — хеш, привязанный к заголовку *именно этого* файла; окончательно собранный файл обязан воспроизвести SHA-256 из заголовка. Непроверенным до выхода не доходит ничего.
4. **Детерминированное восстановление с ограничениями.** Все поисковые стадии на стороне декодера имеют явные лимиты (число комбинаций, число попыток, бюджет реального времени). Декодер либо успевает в пределах лимитов, либо честно сообщает о неудаче; бесконечного вращения не бывает.
5. **Скромный инженерный набор.** SHA-256/SHA-512, усечённые хеши, Рид—Соломон над GF(2¹⁶), Base64. Никаких самодельных шифров и «новаторской» криптографии.

## 4. Пакет: единица передачи

| Свойство | Значение |
|---|---|
| Бинарный размер | 75 B |
| Текстовый размер | ровно 100 символов Base64, без паддинга `=` (75 делится на 3) |
| Виды | заголовок, сектор (две схемы), сигнатура — см. §5 |
| Фрагментация | исключена: пакет атомарен; приёмник ищет целые 100-символьные фрагменты |

Направление кодирования: байты → Base64 (`A–Z a–z 0–9 + /`). Текстовый фильтр принимающей стороны извлекает Base64-материал из произвольного окружения, игнорируя пробелы и лишние символы паддинга; сканер затем ищет 75-байтные окна, чьи внутренние проверки проходят (§11.1). Как пакеты склеиваются в выходной текст (переносы строк, обрамление) — параметр выходного формата, описанный в [EncoderGuide](EncoderGuide.ru.md); декодер от него не зависит.

## 5. Форматы пакетов

Все пакеты — ровно 75 байт. Смещения — от начала пакета.

### 5.1 Пакет-заголовок

Несёт всё необходимое для идентификации и проверки файла. Несколько копий расставляется по потоку (§10.2).

| Поле | Диапазон | Размер | Кодирование | Смысл |
|---|---|---|---|---|
| H1 — имя файла | 0..13 | 14 B | ASCII, справа добивается пробелами | упакованное имя файла; правила упаковки в §7 |
| H2 — размер файла | 14..16 | 3 B | беззнаковое LE (младшие 3 байта 32-битного значения) | точный размер содержимого файла в байтах |
| H3 — хеш содержимого | 17..48 | 32 B | raw | SHA-256 полного содержимого файла |
| H4 — количество чётностей | 49..50 | 2 B | UInt16 LE | M: число томов чётности Рида—Соломона |
| H5 — хеш заголовка | 51..74 | 24 B | raw | `Trunc24(SHA-256(H1 ‖ H2 ‖ H3 ‖ H4))` |

51 байт H1..H4 — *содержимое заголовка*; H5 — его 24-байтовый (192-битовый) усечённый хеш.

**Автономная проверка.** 75-байтное окно является корректным пакетом-заголовком тогда и только тогда, когда байты на 51..74 равны `Trunc24(SHA-256(байты 0..50))`. Внешний контекст не нужен, поэтому сканер распознаёт заголовки в никогда не виденном ранее потоке. Вероятность, что случайный 75-байтный блоб пройдёт, — 2⁻¹⁹².

Производные величины (вычисляются декодером из заголовка):

- Число томов данных `N = max(1, ceil(H2 / 64))` — файл переносится в N томах полезной нагрузки по 64 B.
- Полное число томов `N + M` — тома данных плюс тома чётности; индексы секторов: `0 .. N+M−1`.

### 5.2 Пакет сектора — схема Classic (по умолчанию)

Переносит одну 64-байтовую полезную нагрузку для одного индекса тома одного файла.

| Поле | Диапазон | Размер | Кодирование | Смысл |
|---|---|---|---|---|
| D1 — индекс тома | 0..1 | 2 B | UInt16 LE | индекс тома: `0..N−1` — данные, `N..N+M−1` — чётность |
| D2 — полезная нагрузка | 2..65 | 64 B | raw | байты файла (том данных) или байты чётности (том чётности); последний том данных добивается нулями до 64 B |
| D3 — хеш сектора | 66..74 | 9 B | raw | `Trunc9(SHA-256(H5 ‖ D1 ‖ D2))` |

D3 просеивается через **H5 заголовка этого файла**. Следствия:

- Секторный пакет невозможно проверить, не зная заголовка — это сделано сознательно. Шум и чужие пакеты структурно невидимы для приёмника, пока заголовок не встретился; и наоборот: как только заголовок известен, каждый сектор привязан именно к этому файлу (H3 внутри H5 прибивает идентичность файла гвоздём).
- При известном заголовке случайный 75-байтный блоб проходит проверку D3 с вероятностью 2⁻⁷² (72 бита).

### 5.3 Пакет сектора — схема VirtualIndex (опциональная)

То же назначение, другая привязка индекса.

| Поле | Диапазон | Размер | Кодирование | Смысл |
|---|---|---|---|---|
| V2 — полезная нагрузка | 0..63 | 64 B | raw | полезная нагрузка, как D2 |
| V3 — тег позиции | 64..74 | 11 B | raw | `Trunc11(SHA-256(H5 ‖ payload ‖ index_LE))`, где `index_LE` — индекс тома в little-endian |

Индекс **не хранится** в пакете. Он — вход тега: приёмник определяет индекс, перебирая кандидатов, пока тег не сойдётся (§11.3). Обе схемы переносят ровно 64 байта полезной нагрузки на пакет — Classic тратит 2 B на индекс и 9 B на хеш, VirtualIndex — 0 B на индекс и 11 B на тег; итог сходится к 75 B.

Зачем две схемы:

- **Classic** масштабируется на весь диапазон томов (до 65 535) и проверяется одним вычислением хеша на пакет.
- **VirtualIndex** сильнее на пакет (88-битовый тег) и освобождает 2 индексных байта, но приёмнику приходится восстанавливать индекс поиском. Поиск ограничен порогом `VirtualIndexSectorLimit` (по умолчанию **512** полных томов): файлы с большим числом томов в этой схеме просто **не кодируются** — кодек отказывает, а не даунгрейдит молча. На принимающей стороне восстановление индекса применяется к слотам в пределах того же порога; схема выбирается явно (по умолчанию Classic) и должна совпадать на обоих концах.

Стойкость тега к ложным срабатываниям при известном заголовке: случайный блоб совпадает с *каким-нибудь* индексом из `K = N + M` кандидатов с вероятностью `K · 2⁻⁸⁸ = 2⁻⁸⁸⁺ˡᵒᵍ₂ᴷ`, то есть **88 − log₂K бит**; на пределе K = 512 это ≥ 79 бит — всё ещё сильнее, чем 72 бита у Classic.

### 5.4 Сигнатурный пакет (опциональный)

Независимое доказательство полного содержимого файла, вычисляемое на SHA-512.

| Поле | Диапазон | Размер | Кодирование | Смысл |
|---|---|---|---|---|
| S1 — сигнатура содержимого | 0..63 | 64 B | raw | `SHA-512(полное содержимое файла)` |
| S2 — тег сигнатуры | 64..74 | 11 B | raw | `Trunc11(SHA-512(S1))` |

S2 делает пакет **автономным** (проверяемым без всякого заголовка, шанс случайного прохода 2⁻⁸⁸), поэтому сигнатурные пакеты распознаются в любом месте потока — в точности как заголовки. S1 проверяется позже, против собранного файла. Одна копия сигнатуры ставится сразу за каждой копией заголовка (§10.2).

### 5.5 Сводка стойкости проверок

| Проверка | Биты | Нужный контекст | Случайный блоб проходит с |
|---|---|---|---|
| Заголовок H5 | 192 | нет | 2⁻¹⁹² |
| Сигнатура S2 | 88 | нет | 2⁻⁸⁸ |
| Сектор Classic D3 | 72 | заголовок того же файла | 2⁻⁷² |
| Тег VirtualIndex V3 | 88 − log₂K | заголовок того же файла | ≥ 2⁻⁷⁹ при K = 512 |
| Итоговая проверка содержимого | 256 | H3 из заголовка | 2⁻²⁵⁶ |
| Итоговая проверка сигнатуры | 512 | любой S1 из сигнатурных пакетов | 2⁻⁵¹² |

## 6. Система хеширования

### 6.1 Два уровня: Compact и Secure

Каждое вычисление SHA-256/SHA-512 в кодеке идёт через одну пару примитивов:

- **Compact** — обычный SHA, побитово стандартный алгоритм.
- **Secure** — *ключевой, с секретом*. Секрет (строка) кодируется в UTF-8 и подаётся **префиксом ко каждому хешируемому сообщению**: `digest = SHA(secret_utf8 ‖ message)`. Без установленного секрета Secure побитово совпадает с Compact.

Это сознательный консервативный дизайн: префиксное ключевое хеширование в духе HMAC, но построенное на немодифицированном SHA, чтобы путь «без секрета» был в точности стандартным алгоритмом. Все значения «на проводе» (H3, H5, D3, V3, S1, S2) считаются через примитив Secure, поэтому **один переключатель ключивает весь провод целиком**.

Секрет хранится в `AsyncLocal`-области секрета: он устанавливается на время операции кодирования или декодирования и естественным образом ограничен этим асинхронным потоком выполнения. Охранная структура (`SecretScopeGuard`) устанавливает секрет в начале операции и восстанавливает предыдущую область при освобождении. Существенны два правила:

- **Пустой секрет означает «секрета нет»**: установка пустой строки не затирает секрет, установленный внешней областью.
- Секрет применяется симметрично: **на стороне декодирования необходимо задать тот же секрет**, иначе провалятся все хеш-проверки (поток станет непроверяемым — и будет отвергнут, а не принят с ослабленными проверками).

### 6.2 Что чем хешируется и где живёт

| Значение | Примитив | Вход | Где живёт |
|---|---|---|---|
| H3 | SHA-256 (Secure) | полное содержимое файла | заголовок, байты 17..48 |
| H5 | SHA-256 (Secure), усечение до 24 B | H1 ‖ H2 ‖ H3 ‖ H4 | заголовок, байты 51..74 |
| D3 | SHA-256 (Secure), усечение до 9 B | H5 ‖ D1 ‖ D2 | сектор Classic, байты 66..74 |
| V3 | SHA-256 (Secure), усечение до 11 B | H5 ‖ payload ‖ index_LE | сектор VirtualIndex, байты 64..74 |
| S1 | SHA-512 (Secure) | полное содержимое файла | сигнатура, байты 0..63 |
| S2 | SHA-512 (Secure), усечение до 11 B | S1 | сигнатура, байты 64..74 |

> [!NOTE]
> Значения, показываемые *пользователю* в отчётах и статистике («реальные» SHA-256/SHA-512 файла), всегда вычисляются **без** секрета, чтобы отчёт оставался сравнимым между машинами и сеансами. Секрет влияет только на то, что путешествует по проводу и что принимают внутренние проверки.

### 6.3 Почему усечение здесь безопасно

Усечённые хеши ослабляют *стойкость к коллизиям*, но проверки «на проводе» — барьеры *второго прообраза* против случайного шума и неподготовленной подделки: злоумышленник (без секрета) обязан подобрать сообщение, чей ключевой хеш разделяет хранимый префикс. Против 192-битового барьера заголовка или 72–88-битовых барьеров сектора практический ответ таков: случайный текст через них просто не проходит; итоговую сертификацию выходного файла выполняют полноразмерные проверки 256/512 бит (H3, S1). Усечение существует, чтобы уместить проверки в фиксированный 75-байтный пакет рядом с полезными 64 байтами.

## 7. Упаковка имени файла (поле H1)

В заголовке 14 байт под имя. Настоящие имена не всегда помещаются, поэтому имя *упаковывается*, а не хранится дословно; точное исходное имя восстанавливается по H3 (ниже).

Правила `FileNameCodec.Pack`:

1. Имя разбивается по **первой** точке. Всё от точки и дальше — *расширение*, оно сохраняется **целиком** — составные расширения вида `.tar.gz` выживают как единое целое. Если точки нет или точка первая — всё имя считается базой, расширения нет.
2. *База* (часть до расширения) получает остаток бюджета байт: `budget = 14 − длина_расширения`.
3. Если база помещается в бюджет — хранится как есть. Если нет — обрезается до `budget − 1` байт, и в конец добавляется тильда `~` как маркер усечения (без цифр: маркер говорит только «здесь резали»).
4. Если бюджет меньше 2 байт (1 символ + маркер) — имя **непредставимо**, кодирование отказывает с явной ошибкой: изуродованная подсказка в 0–1 символ считается хуже честного отказа.
5. Результат справа добивается пробелами ровно до 14 байт и обязан кодироваться в ASCII.

Упакованное имя — *подсказка для человека*: по любой уцелевшей копии заголовка можно узнать файл «в лицо». **Авторитетное** имя приходит от отправителя вне канала или из знаний приёмника, а идентичность содержимого всегда решает H3: декодер проверяет собранное содержимое против SHA-256 из заголовка, поэтому совпавший H3 удостоверяет байты, на которые указывает (пусть и обрезанно выглядящее) имя.

## 8. Арифметика томов и пределы

Обозначения: размер файла `S` байт, процент чётности `p` (0–100), процент заголовков `q` (0–100).

| Величина | Формула | Примечания |
|---|---|---|
| Тома данных `N` | `max(1, ceil(S / 64))` | последний том данных добивается нулями до 64 B |
| Тома чётности `M` | `max(1, round(N · p / 100))` при `p ≥ 1`; `0` при `p = 0` | округление к ближайшему (половина — вверх); даже 1 % даёт хотя бы один том чётности |
| Полное число томов `T` | `N + M` | индексы секторов `0..T−1`; чётность занимает `N..T−1` |
| Копии заголовка `H` | `max(3, round(T · q / 100))` | округление к ближайшему (половина — вверх); минимум 3 копии: начало, середина, конец |

Жёсткие пределы, все — с явными ошибками:

| Предел | Значение | Происхождение |
|---|---|---|
| Поле размера файла | 16 777 215 B (≈16,8 МБ) | H2 — 3 байта |
| Полное число томов `T` | 65 535 | поле индекса сектора и длина кодового слова RS (§9) |
| Число томов чётности `M` | 65 535 | H4 — UInt16 |
| Тома VirtualIndex | `VirtualIndexSectorLimit`, по умолчанию 512 | стоимость поиска индекса (§5.3) |

> [!NOTE]
> Для больших файлов связывающим ограничением является предел томов, а не поле размера: `T ≤ 65 535` означает не больше `65 535 · 64 ≈ 4,0 MiB` данных даже при нулевой чётности. 3-байтовое поле размера просто не успевает переполниться.

## 9. Слой Рида—Соломона

Назначение: переживать *потерю* целых секторных пакетов, до контролируемой доли, без переспроса.

Модель:

- **Том** — один 64-байтовый слот кодового слова; на проводе его переносит один секторный пакет (Classic или VirtualIndex). Тома данных содержат байты файла; тома чётности — вычисленную избыточность.
- Код работает над **GF(2¹⁶)**: один символ = 2 байта, little-endian. Каждый 64-байтовый том — **32 символа**.
- Для каждого из 32 символьных позиций независимо значения в этой позиции по всем `T = N + M` томам образуют одно кодовое слово Рида—Соломона длины `T` с `N` информационными и `M` проверочными символами. Равносильно: том чётности `j` вычисляется так, чтобы вся стопка томов образовала систематический RS-код, позиция за позицией.
- Декодирование — **декодирование стираний**: декодер знает, *какие* тома потеряны (для остальных у него есть проверенные пакеты), а не *как* они искажены. Декодирование стираний восстанавливает любые `e ≤ M` потерянных томов кодового слова из оставшихся `T − e ≥ N`.

Следствия и правила:

- **Условие восстановления.** Набор потерянных томов данных восстановим ровно тогда, когда `стёртые тома данных ≤ пригодные тома чётности` (чётность, сама присутствующая на руках). При `p = 10 %` поток переживает потерю любых 10 % своих пакетов с нагрузкой — любых 10 %, а не только хвоста.
- **Предел длины.** `N + M ≤ 65 535` — потолок длины RS над GF(2¹⁶), совпадающий с пределом томов из §8.
- **Стирания, а не ошибки.** «Испорченных на месте» пакетов для декодера не существует: пакет, не прошедший хеш-проверку, отбрасывается и становится стиранием. Именно поэтому попакетная проверка (§5) и RS так плотно пригнаны друг к другу.
- **Стоимость.** Одна попытка декодирования стоит примерно `O(E²·N)` подготовки плюс 32 прохода по `O(E·N)` плюс хеширование, где `E` — число стёртых томов. Стадия поиска подмножеств ограничивает `E` значением 32 (`MaxErasedDataVolumes`, откалибровано бенчмарком), так что даже при максимальном легальном `T = 65 535` в 30-секундный бюджет умещаются десятки попыток (§11.4).
- **Реализация.** Арифметика живёт в эталонных исходниках `RsRaid16`, обёрнутых `RsCodecAdapter`; сам кодек GF-математики не касается.

## 10. Конвейер кодирования

Вход: содержимое файла (байты), имя файла, параметры (`eccPercent`, `headerPercent`, `sectorScheme`, `virtualIndexSectorLimit`, `signaturePackets512`, `hashSecret`).

Шаги `StreamEncoder.Encode` по порядку:

1. **Установить область секрета.** Создаётся `SecretScopeGuard`: если `hashSecret` непуст, все хеш-вычисления внутри операции ключевые (§6.1); при освобождении восстанавливается предыдущая область.
2. **Проверить размер.** `S ≤ 16 777 215`, иначе отказ.
3. **Упаковать имя** в 14 байт (§7); при непредставимости — отказ.
4. **Хешировать содержимое**: `sha256 = SHA-256-Secure(content)` — это будущий H3.
5. **Вычислить размерности**: `N`, `M`, `T` (§8); проверить `T ≤ 65 535`; если схема VirtualIndex — проверить `T ≤ 512` (без молчаливого даунгрейда).
6. **Нарезать полезную нагрузку**: `N` буферов по 64 B; последний принимает хвост файла и **добивается нулями** до 64 B. (Истинная длина — H2; декодер срежет паддинг после сборки.)
7. **Вычислить чётность**: `Rs.Encode(payloads, M)` → `M` буферов чётности по 64 B. Это самая тяжёлая фаза; прогресс-отчётность отображает её на диапазон 10..75 % глобальной шкалы.
8. **Собрать заголовок**: 51 байт содержимого (H1 имя, H2 размер, H3 хеш, H4 чётность) + `H5 = Trunc24(SHA-256-Secure(H1..H4))` → 75-байтный пакет-заголовок.
9. **Собрать сигнатурный пакет** (если включён): `S1 = SHA-512-Secure(content)`, `S2 = Trunc11(SHA-512-Secure(S1))`. Вычисляется внутри области секрета, как и всё остальное.
10. **Собрать секторные пакеты** для всех `T` томов (сначала данные, затем чётность), по выбранной схеме Classic или VirtualIndex (диапазон прогресса 75..100 %).
11. **Расставить поток** — см. §10.2.
12. **Вайп промежуточных буферов**: буферы открытой полезной нагрузки, буферы чётности и сырые байты заголовка обнуляются (`Array.Clear`) перед возвратом метода. Сами возвращённые пакеты — это и есть передача, по замыслу.

### 10.1 Что выдаёт кодировщик

Плоский список 75-байтных пакетов:

```
packetCount = T + H                     (без сигнатур)
packetCount = T + 2·H                   (с сигнатурами: по одной на копию заголовка)
```

Вызывающая сторона превращает каждый пакет в его 100-символьный Base64-фрагмент и склеивает согласно выходному формату (ширина строк, обрамление — см. [EncoderGuide](EncoderGuide.ru.md)). Декодеру это оформление безразлично.

### 10.2 Раскладка потока: `ArrangePackets`

Расстановка копий заголовка следует одному правилу: **поток начинается заголовком, заканчивается заголовком, а между ними равномерно расставлены промежуточные копии.**

1. Вывести `заголовок (+ сигнатура, если включены)`.
2. Если `H ≤ 2`: вывести все секторные пакеты. (На практике всегда `H ≥ 3` из-за минимума; ветка существует для полноты.)
3. Иначе, при `middle = H − 2` промежуточных копиях и `interval = max(1, T div (middle + 1))`: идти по секторным пакетам в порядке индексов и после каждого `interval`-го сектора — пока остаются промежуточные копии — выводить `заголовок (+ сигнатура)`.
4. Вывести финальный `заголовок (+ сигнатура)`.

Два следствия, которые стоит сказать явно:

- **За каждой копией заголовка немедленно следует одна копия сигнатуры** (когда сигнатуры включены). Заголовок и сигнатура путешествуют связанной парой, поэтому любой непрерывный кусок потока, содержащий копию заголовка, содержит и полную идентичность файла (H2/H3/H4), *и* его SHA-512-доказательство.
- **Равномерная экспозиция.** При `H ≥ 3` копии сидят в начале, в конце и равномерно внутри тела. Непрерывная вырезка примерно из `2·interval + 2` пакетов, взятая *где угодно* в потоке, гарантированно содержит хотя бы одну копию заголовка (и сигнатуры); именно интервальная арифметика шага 3 гарантирует, что все промежуточные копии не могут попасть вне достаточно длинного окна.

## 11. Конвейер декодирования

Вход: произвольный текст (или поток, прочитанный из него) плюс опции: ожидаемая `sectorScheme`, `signatureMode`, опциональный `hashSecret`, лимиты поиска.

### 11.1 Текстовый фильтр и сканер пакетов

- **Фильтр** счищает вход до Base64-материала: пробелы, пунктуация и лишний паддинг `=` игнорируются; оставшиеся символы алфавита декодируются скользящим образом. Декодер никогда не предполагает чистый вход.
- **Сканер** ведёт 75-байтное окно по байтовому потоку и классифицирует каждое окно **в таком порядке**:
  1. **Заголовок?** — проверка H5 (автономная, 192 бита). При успехе создаётся (или находится) *слот приёма* для этого заголовка; байты пакета — идентичность слота.
  2. **Сигнатура?** — проверка S2 (автономная, 88 бит). При успехе S1 (64 байта) пополняет набор собранных сигнатур слота. Копии одной сигнатуры схлопываются в одну запись — набор хранит различные значения, поэтому повторные отправки и дублированные фрагменты не накапливаются.
  3. **Сектор?** — для каждого *известного* слота (H5 каждого слота — сид) проверка сектора по схеме: Classic сверяет `Trunc9(SHA-256(H5‖D1‖D2))` с D3 и читает индекс из D1; VirtualIndex вычисляет `Trunc11(SHA-256(H5‖payload‖idx))` для индексов-кандидатов (§11.3) и принимает пакет на совпавшем индексе. Окно, прошедшее проверку для некоторого слота, подшивается в этот слот на этот индекс.

  Порядок важен: автономные проверки идут первыми, потому что не требуют контекста; проверка сектора — последняя, потому что она привязана к файлу. Сигнатурный пакет, который случайно парсится как сектор какого-то файла, безвреден: он будет принят лишь пройдя собственную хеш-проверку этого файла, а у настоящей сигнатуры нет причин с чем-то коллидировать (а если бы и была — итоговая 256-битовая проверка это поймает).

### 11.2 Слоты приёма

**Слот** — состояние декодера для одного заголовка: байты заголовка, хранилище полезных нагрузок по индексам, учёт коллизий и набор сигнатур. Слоты ключуются содержимым заголовка, поэтому:

- дублированные копии заголовка попадают в один слот;
- **из одного потока одновременно принимаются несколько разных файлов** — каждому распознанному заголовку достаётся свой слот, сборка идёт по слоту независимо;
- каждый слот отдельно учитывает, сколько *копий* секторов пришло (для статистики) и сколько различных проверенных *вариантов* существует на индекс.

### 11.3 Восстановление VirtualIndex

Для слота VirtualIndex с `K = T ≤ 512`:

- **Последовательное поступление (обычный случай).** Слот держит курсор — следующий ожидаемый индекс. Для каждого входящего пакета сначала проверяется тег на индексе курсора: одно вычисление хеша, O(1) на пакет, когда поток приходит по порядку.
- **Вне порядка / произвольный доступ.** Тег проверяется против индексов-кандидатов; поиск по `0..K−1` распараллелен. Не больше `K · 2⁻⁸⁸⁺ˡᵒᵍ₂ᴷ` ложных приёмов на чужой пакет (§5.3).

### 11.4 Стадии сборки

Когда слот получил материал, декодер пытается собрать файл. Попытки эскалируют (механика и настройка — в [AssemblyGuide](AssemblyGuide.ru.md)):

1. **Прямая сборка.** На каждом индексе данных ровно одна проверенная полезная нагрузка: конкатенация в порядке индексов, обрезка до `H2` байт (снятие нулевого паддинга последнего тома), хеширование, сверка с H3.
2. **RS-восстановление.** Часть томов данных потеряна, неоднозначностей нет, и `пропало ≤ пригодной чётности`: недостающие нагрузки перестраиваются декодированием стираний RS (§9), далее как в стадии 1.
3. **Поиск версий.** На некоторых индексах — по несколько *различных* проверенных нагрузок (**коллизионный слот**: один индекс, достигнутый пакетами из повреждённых/дублированных передач или неподготовленным фальсификатором без секрета). Каждый кандидат на индекс — *версия*; декодер перебирает комбинации версий. Стратегия: исчерпывающий перебор, пока число комбинаций укладывается в `MaxExhaustiveCombinations` (по умолчанию 100 000), затем эвристический сэмплинг в пределах `MaxHeuristicAttempts` (по умолчанию 100 000), всё — под бюджетом реального времени `TimeBudget` (по умолчанию 30 с). Комбинаторика и порядок шагов централизованы в чистом математическом помощнике (подсчёт, интервальная арифметика на НОД/НОК, выбор стратегии).
4. **Поиск подмножеств томов.** Когда коллизии не разрешились или потеряно слишком много томов, декодер меняет вопрос: *какие тома объявить стёртыми*, чтобы RS их восстановил? Планировщик перебирает **маски исключения**:
   - *базовая* маска исключает все тома, затронутые коллизиями, — неоднозначные данные восстанавливаются из чётности, а не угадываются;
   - *уровень 1* дополнительно исключает один неколлизионный том, выбирая по подозрительности (менее подтверждённые — вперёд; при равенстве — детерминированный псевдослучайный порядок с сидом от H5, так что прогоны воспроизводимы);
   - *уровни 2 и глубже* исключают ещё тома из короткого списка, до `MaxExtraExclusionLevel`;
   - маска *осуществима*, когда стёртых томов данных (пропавшие + исключённые) не больше пригодной чётности и не больше `MaxErasedDataVolumes = 32`;
   - маски, не стирающие ни одного тома данных, пропускаются (восстанавливать нечего).
   Каждая осуществимая маска стоит одной RS-попытки (§9, заметка о стоимости) плюс проверка; лимиты: не более 100 000 попыток и 30 с суммарно (`VolumeSubsetSearchOptions`).

Все пути стекаются в одну и ту же **итоговую проверку**:

- **Exact(SHA-256):** SHA-256 собранного содержимого обязан совпасть с H3 байт-в-байт. Это безоговорочно; при несовпадении наружу не выдаётся ничего.
- **Any(SHA-512)** (расширенная проверка, зависит от режима — см. §11.5): SHA-512 собранного содержимого обязан совпасть хотя бы с одной сигнатурой из набора слота.

Снимок сигнатур, используемый этими проверками, берётся один раз на попытку сборки и прокидывается через все стадии, поэтому вердикт каждой стадии вычисляется против одного и того же стабильного вида на принятые сигнатуры.

### 11.5 Режимы сигнатур

| Режим | Поведение декодера |
|---|---|
| `Base` | Сигнатурные пакеты детектируются и собираются, но расширенная проверка **не выполняется**; файл принимается по одному Exact(SHA-256). |
| `Auto` (по умолчанию) | Расширенная проверка активна, **если для файла принят хотя бы один сигнатурный пакет**. Поток, в котором сигнатур просто нет, декодируется обычным образом; поток, в котором сигнатуры есть, обязан их почтить. |
| `Force` | Расширенная проверка активна **всегда**. Если ни одна собранная сигнатура не совпала с собранным содержимым — включая случай, когда сигнатурных пакетов не пришло вовсе — декодирование падает с `SignatureVerificationException`, даже если SHA-256 прошёл. |

Прочтение режимов: `Base` — совместимость с трафиком без сигнатур; `Auto` — следование уликам, имеющимся в потоке; `Force` — параноидальный режим для каналов, где намерение отправителя подписывать должно исполняться неукоснительно.

## 12. Приём нескольких файлов из одного потока

В сканере нет ничего, что предполагало бы единственный файл. Каждый различимый заголовок, найденный в тексте, порождает свой слот приёма (§11.2); секторы привязываются к слотам через сид H5, сигнатуры — через автономность; сборка и проверка выполняются по слоту независимо. Вставленная подряд конкатенация двух передач даёт оба файла, каждый проверен против своего H3 (и своих сигнатур, по режиму). Декодер также справляется с вырожденным случаем, когда фрагменты одного файла рассеяны по чужому тексту: шум просто никогда не классифицируется (§11.1), а пропавшие пакеты — забота слоя RS (§9).

## 13. Свойства безопасности и границы

Что дизайн гарантирует, сказано прямо:

- **Целостность выхода.** Файл выдаётся только после Exact(SHA-256) против заголовка, с расширенной SHA-512-проверкой по режиму сигнатур. Собрать неправильные байты, проходящие 256-битовый барьер, — значит найти второй прообраз (возможно, ключевого) хеша.
- **Неподделываемость пакетов (с секретом).** При заданном `hashSecret` все проверки «на проводе» ключевые. Сторона без секрета не может изготовить заголовок, сектор или сигнатуру, которые декодер примет, — разве что сломав префиксное хеширование SHA-256/SHA-512. Без секрета защита — только от случайного шума и смешивания.
- **Изоляция файлов друг от друга.** Секторы привязаны к H5 своего файла; фрагменты разных файлов не проходят проверки чужих слотов, а преднамеренная попытка коллизии обязана пережить попакетный барьер и затем финальные барьеры 256/512 бит.
- **Нет конфиденциальности.** Сказано ещё раз, потому что важно: полезная нагрузка внутри пакетов — открытый текст. Если нужна тайна — шифруйте заранее.
- **Гигиена.** Секрет живёт в async-local области на время операции (не в статическом изменяемом состоянии вне механизма области); кодировщик обнуляет свои буферы открытой нагрузки, буферы чётности и сырые байты заголовка перед возвратом. Сигнатурные пакеты строятся внутри охраны секрета, так что поведение «ключевой/бесключевой» симметрично на обоих концах провода.

## 14. Разбор примеров

### 14.1 Файл 128 байт, настройки по умолчанию, сигнатуры включены

Параметры: `eccPercent = 10`, `headerPercent = 3`, схема Classic, `signaturePackets512 = вкл`.

Арифметика:

| Шаг | Вычисление | Результат |
|---|---|---|
| Тома данных | `ceil(128 / 64)` | `N = 2` |
| Тома чётности | `max(1, round(2 · 10 / 100)) = max(1, 0)` | `M = 1` |
| Полное число томов | `2 + 1` | `T = 3` |
| Копии заголовка | `max(3, round(3 · 3 / 100)) = max(3, 0)` | `H = 3` |
| Интервал | `max(1, 3 div (1 + 1)) = max(1, 1)` | `1` |
| Пакетов | `T + 2·H = 3 + 6` | `9` |

Выданный поток по порядку:

| № | Пакет |
|---|---|
| 1 | Заголовок |
| 2 | Сигнатура |
| 3 | Сектор 0 (данные, байты файла 0..63) |
| 4 | Заголовок |
| 5 | Сигнатура |
| 6 | Сектор 1 (данные, байты файла 64..127) |
| 7 | Сектор 2 (чётность) |
| 8 | Заголовок |
| 9 | Сигнатура |

Стоимость на проводе: `9 · 75 = 675` бинарных байт, `9 · 100 = 900` символов Base64 на 128 байт полезной нагрузки — расширение ≈ 5,3× в бинарном исчислении (≈ 7,0× в символах). Малые файлы задавлены фиксированными метаданными: три копии заголовка и три копии сигнатуры перевешивают два пакета с нагрузкой. Такова цена правила идентификации «начало—середина—конец», и она быстро тает с ростом файла (следующий пример).

Живучесть этого потока: любые 3 пакета могут потеряться подряд — файл всё равно собирается напрямую или через RS (один том чётности восстанавливает любой один потерянный том данных); даже при потере обоих томов данных чётности одной мало (`2 > 1`), но *любой* уцелевший сектор данных вместе с чётностью завершает файл.

### 14.2 Файл 1 MiB, настройки по умолчанию

`S = 1 048 576` B, `eccPercent = 10`, `headerPercent = 3`.

| Шаг | Вычисление | Результат |
|---|---|---|
| Тома данных | `1 048 576 / 64` | `N = 16 384` |
| Тома чётности | `round(16 384 · 10 / 100)` | `M = 1 638` |
| Полное число томов | | `T = 18 022` |
| Копии заголовка | `round(18 022 · 3 / 100)` | `H = 541` |
| Пакетов с сигнатурами | `18 022 + 2 · 541` | `19 104` |
| Текст на проводе | `19 104 · 100` | `1 910 400` символов ≈ 1,91 МБ |

Расширение ≈ **1,82×** в символах (1,37× в бинарных байтах). Расклад: одна упаковка нагрузки стоит 100 символов на 64 байта (1,56×); 10 % чётности поднимают до ≈ 1,72×; заголовки и сигнатуры добавляют ≈ 0,10×. Поток переживает потерю любых 1 638 пакетов с нагрузкой (≈ 8,6 % потока) прямым RS-восстановлением, не считая того, что вытягивают поисковые стадии из более тяжёлых повреждений.

### 14.3 Потолок

Предел томов (§8) делает ≈ 4,0 MiB самым большим кодируемым файлом (65 535 томов данных, нулевая чётность — `eccPercent = 0`). Большие входы отвергаются с явной ошибкой, а не обрезаются.

## 16. Глоссарий

| Термин | Смысл |
|---|---|
| Пакет | Атомарная 75-байтная единица передачи; на проводе — 100 символов Base64. |
| Том | Один 64-байтовый слот кодового слова RS: тома данных несут байты файла, тома чётности — избыточность RS. Переносятся секторными пакетами 1:1; «индекс тома» = «номер сектора». |
| Секторный пакет | Вид пакета, переносящий один том. |
| Заголовок | Вид пакета с идентичностью файла: имя, размер, SHA-256, число чётностей и собственный 192-битовый хеш H5. |
| Сигнатурный пакет | Опциональный вид пакета с SHA-512 содержимого (S1) и автономным 88-битовым тегом (S2). |
| Схема Classic | Привязка сектора явным 2-байтовым индексом + 9-байтовым хешем с сидом H5. |
| Схема VirtualIndex | Привязка сектора 11-байтовым тегом, в который индекс входит как вход хеша; индекс восстанавливает приёмник; предел — 512 томов. |
| Усечение (`TruncN`) | Первые N байт хеша; нужно, чтобы уместить проверки в фиксированный пакет. |
| Область секрета | Async-local настройка, ключирующая все вычисления Secure на время одной операции. |
| Стирание | Том, о котором известно, что он потерян (пакет отсутствует или не прошёл проверку), — входное условие декодирования RS. |
| Коллизионный слот | Индекс, на который принято несколько различных проверенных нагрузок; разрешается поиском версий или исключением. |
| Версия | Один кандидат-нагрузка на один индекс в коллизионном слоте. |
| Маска исключения | Объявленный набор томов, рассматриваемых как стёртые, чтобы RS их восстановил; перебирается планировщиком подмножеств. |
| Слот приёма | Состояние декодера для одного заголовка: нагрузки, коллизии, сигнатуры, сборка. |
| Exact(SHA-256) / Any(SHA-512) | Итоговые барьеры: хеш содержимого обязан в точности равняться H3; SHA-512 содержимого обязан совпасть хотя бы с одной собранной сигнатурой (по режиму). |
| `H1..H5`, `D1..D3`, `S1..S2` | Имена полей внутри пакетов заголовка, сектора и сигнатуры (§5). |
