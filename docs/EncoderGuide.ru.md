## 1. Соглашения, используемые в документе

- `N` — data-тома, `M` — ECC-тома, `T = N + M` — всего томов; каждый том несёт ровно один пакет-сектор ([AlgorithmGuide §8](AlgorithmGuide.ru.md)).
- `H` — число копий заголовка в потоке; **сигнатурный пакет** следует за каждой копией заголовка при включённых сигнатурах.
- Хеши «на проводе» — значения, хранимые в пакетах (ключевые при заданном секрете); **реальные** — простые пересчёты для отчётов.
- Размеры: `B` = байты, `MiB` = 1 048 576 B; пейлоад — 64 B; пакет — 75 B = 100 символов Base64.

## 2. Что производит одно кодирование

Операция кодирования превращает «содержимое + имя файла» в упорядоченный список 75-байтовых пакетов:

```text
[заголовок (+сигнатура)]  сектор₀ … секторᵢ [заголовок (+сигнатура)] секторᵢ₊₁ … … [заголовок (+сигнатура)]
```

- Каждый data-том и каждый ECC-том становятся пакетом-сектором (схема Classic или VirtualIndex).
- Поток **открывается** пакетом-заголовком и **закрывается** пакетом-заголовком; прочие копии распределяются равномерно по телу (§7).
- При включённом `signaturePackets512` за каждой копией заголовка немедленно следует один сигнатурный пакет (`S1 ‖ Trunc11(SHA-512(S1))`).

Приёмная сторона от этого порядка не зависит — она переупорядочивает всё, — но раскладка максимизирует выживаемость при типовом паттерне повреждений (обрезание с любого конца, выпадения из середины).

## 3. Создание кодировщика

```csharp
public StreamEncoder(
    int eccPercent = 10,
    int headerPercent = 3,
    SectorScheme sectorScheme = SectorScheme.Classic,
    int virtualIndexSectorLimit = VirtualIndexHasher.DefaultSectorLimit,
    bool signaturePackets512 = false,
    string? hashSecret = null)
```

| Параметр | Дефолт | Значение |
|---|---|---|
| `eccPercent` | **10** | 0 — без RS-избыточности; ≥ 1 — `M = max(1, round(N·pct/100))`, минимум один ECC-том. Отрицательные значения отвергаются. |
| `headerPercent` | **3** | Копии заголовка в процентах от `T`; всегда не менее 3 (начало/середина/конец). |
| `sectorScheme` | **Classic** | `VirtualIndex` отказывается от хранения индекса сектора и отдаёт байты 11-байтовому хеш-тегу ([AlgorithmGuide §5.3](AlgorithmGuide.ru.md)). |
| `virtualIndexSectorLimit` | **512** | Файлы с `T` выше порога под VirtualIndex **отвергаются** — молчаливого даунгрейда на Classic нет (ожидания безопасности оператора не должны меняться тихо). |
| `signaturePackets512` | **выкл.** | Эмитить сигнатурный пакет SHA-512 за каждой копией заголовка; включает на декодере проверку Exact(SHA-256) & Any(SHA-512). |
| `hashSecret` | **нет** | Ключует все хеши «на проводе» для операций экземпляра; декодер должен быть сконфигурирован тем же секретом. |

Два жёстких лимита формата всплывают как `InvalidOperationException` при кодировании: размер файла свыше 16 777 215 B (трёхбайтовое поле `H2`) и `T` свыше 65 535 (`MaxDataVolumes`). Поскольку `T ≥ N = ⌈размер/64⌉`, практический потолок пейлоада ≈ 4,0 МиБ без ECC, меньше с избыточностью.

## 4. Операции кодирования

Базовый класс (`StreamEncoder`, без состояния между вызовами — параллельные кодирования на одном экземпляре безопасны):

| Операция | Возвращает |
|---|---|
| `Encode(content, fileName)` (+progress/ct) | `List<byte[]>` — сырые 75-байтовые пакеты. |
| `EncodeToText(content, fileName)` | Base64-текст, по 100-символьной строке на пакет (без декоративного обрамления — это забота файлового уровня `PacketIO`, §8). |
| `EncodeWithStats(content, fileName)` | `(packets, EncodeStats)` — пакеты плюс сводка операции (§9). |
| Потоковый вход | Каждая перегрузка со `Stream` сначала читает содержимое целиком (`ReadStreamContent`, с проверкой размера, работает и с непозиционируемыми) — SHA-256 и RS всё равно требуют полный буфер. |

Фасад (`DataShieldCodec`) добавляет удобства коллекций:

| Операция фасада | Поведение |
|---|---|
| `EncodeToPackets(content, fileName)` | пакеты; вход — байты / перечисление / поток. |
| `EncodeToText(content, fileName)` | Base64-текст (через `PacketIO`, **с** декоративным обрамлением, когда пишет `Encode`). |
| `EncodeToBytes(content, fileName)` | двоичная конкатенация (75 B × пакетов). |
| `EncodeInto(content, fileName, output)` | добавляет пакеты в коллекцию вызывающего; возвращает количество. |
| `Encode(content-stream, output-stream, format, fileName)` | пишет FEC-поток в запрошенном формате и возвращает `EncodeStats`. |

## 5. Арифметика томов и заголовков

Все формулы — публичные статические члены `StreamEncoder`: размер можно прикинуть без кодирования:

| Величина | Формула | Замечания |
|---|---|---|
| `N` | `max(1, ⌈fileSize / 64⌉)` | пустой файл всё равно занимает один том (нули) |
| `M` | `max(1, round(N · eccPercent / 100))` при `eccPercent ≥ 1`, иначе 0 | округление полувверх: `(N·pct + 50) / 100` |
| `T` | `N + M ≤ 65 535` | жёсткий лимит формата |
| `H` | `max(3, round(T · headerPercent / 100))` | полувверх, минимум 3 |
| промежуточные заголовки | `H − 2` | первый и последний фиксированы |
| интервал вставки | `max(1, T / (промежуточные + 1))` секторов | равномерный разброс |

Разобранный пример — файл 128 B, дефолты (`eccPercent 10`, `headerPercent 3`, сигнатуры включены):

| Шаг | Значение |
|---|---|
| `N` | `⌈128/64⌉ = 2` |
| `M` | `max(1, round(0.2)) = 1` |
| `T` | `3` |
| `H` | `max(3, round(0.09)) = 3` → промежуточных заголовков нет (только начало и конец) |
| Пакетов | `2 data + 1 ECC + 3 заголовка + 3 сигнатуры = 9` |

Файл 1 МиБ: `N = 16 384`, `M = 1 638`, `T = 18 022`, `H = 541` → `19 104` пакета-сектора плюс `541` заголовок (+ `541` сигнатура при включённых) — расширение ≈ 1,82× в двоичных байтах.

## 6. Построение пакетов

Три сборщика (все `internal`, работают через `Encode`):

| Сборщик | Выход |
|---|---|
| `BuildHeaderPacket` | `H1..H4 (51 B) ‖ H5 = Trunc24(SHA-256(H1..H4))` — пакет, идентифицирующий файл. |
| `BuildDataSector` | `D1 = seqNum LE(2) ‖ D2 = payload(64) ‖ D3 = Trunc9(SHA-256(H5 ‖ D1 ‖ D2))` — схема Classic. |
| `BuildVirtualIndexSector` | `payload(64) ‖ Trunc11(SHA-256(H5 ‖ payload ‖ idx LE))` — схема VirtualIndex; индекс существует только внутри хеш-входа. |

Заголовок строится один раз, его `H5` вычисляется один раз, и каждый сектор хешируется под этим `H5` — потому фрагменты разных файлов вниз по течению не смешиваются молча.

Последний data-том добивается нулями до 64 B; истинный размер едет в `H2`, а финальный SHA-256-шлюз паддинг игнорирует.

## 7. Раскладка потока: `ArrangePackets`

Алгоритм размещения:

1. Выдать пакет-заголовок (+ сигнатуру при включённых) — первый пакет потока.
2. Если `H ≤ 2`: дописать все пакеты-секторы.
3. Иначе: дописывать пакеты-секторы, а после каждого `interval`-го сектора вставлять копию заголовка (+ сигнатуру), пока позволяет бюджет промежуточных. Интервал `max(1, T / (промежуточные + 1))` сажает копии на примерно равные позиции; сам порядок секторов остаётся последовательным (дружелюбно к курсору VirtualIndex приёмника).
4. Выдать пакет-заголовок (+ сигнатуру) — последний пакет потока.

Последствия, которые стоит усвоить:

- Любое одиночное обрезание потока оставляет хотя бы один заголовок достижимым с уцелевшей стороны; заголовок всегда стоит на краю окрестности каждого крупного уцелевшего фрагмента.
- Копии сигнатуры всегда едут вплотную к копиям заголовка — пара выживает или гибнет вместе.
- Порядок пакетов-секторов сам по себе декодеру безразличен; последовательность — оптимизация, а не требование.

## 8. Форматы вывода и именование файлов

`OutputFormat` выбирает контейнер:

| Формат | Расширение | Содержимое |
|---|---|---|
| `Base64` | `.DataShield.txt` | UTF-8-текст; пакет на строку; опциональные декоративные первая/последняя строки (ниже). |
| `Binary` | `.DataShield.bin` | сырые 75-байтовые пакеты подряд, без разделителей. |

`PacketIO.WriteBase64Text` добавляет **декоративное обрамление**, когда задано имя исходного файла, — ровно по 100 символов, чтобы никогда не мешать сканированию:

```text
>[REPORT.BIN    ][0000640][SHA-256:9f86d0…8]
i1QyN3Lz…  (100 Base64-символов, один пакет)
…
<[REPORT.BIN    ][0000640][SHA-256:9f86d0…8]
```

Поля в скобках переиспользуют упакованное имя заголовка (14 символов, `FileNameCodec.Pack`), размер семью десятичными цифрами с ведущими нулями и hex SHA-256. Строки — удобство для человека: декодер игнорирует всё вне алфавита Base64, включая и их.

Помощники именования (`OutputFormatConfig`):

| Помощник | Правило |
|---|---|
| `GetDefaultOutputPath(input, format)` | `input + ".DataShield.txt"/".DataShield.bin"`. |
| `DetectFormat(path)` | `.txt` → Base64, `.bin` → Binary, прочее → Base64. |
| `StripFecSuffix(path)` | Отбрасывает хвостовой суффикс `.DataShield.*` (`data.DataShield.bin` → `data`). |
| `GetDefaultDecodeOutputPath(path)` | Отрезает суффикс FEC; если его не было, вставляет `.out` перед расширением (`stream.txt` → `stream.out.txt`), чтобы вывод декодирования не затёр вход. |

## 9. `EncodeStats`: сводка операции

`EncodeWithStats` возвращает метаданные только что произведённого:

| Поле | Значение |
|---|---|
| `FileSize` | Исходный размер в байтах. |
| `Sha256` / `Sha512` | Хеши **на проводе** — значения из пакетов заголовка/сигнатуры; ключевые при заданном секрете. |
| `RealSha256` / `RealSha512` | **Реальные** (без секрета) хеши, пересчитанные в ОЗУ, — годны для отчётов и журналов; то, что вычислила бы третья сторона. |
| `DataCount` / `EccCount` | `N` и `M`. |
| `TotalPackets` | Всё в потоке, включая заголовки и сигнатуры. |
| `HeaderCopies` / `SignatureCopies` | Число копий; выводится из формы потока: остаток = `TotalPackets − N − M`; при включённых сигнатурах остаток делится пополам (за каждым заголовком ровно одна сигнатура), иначе остаток — заголовки. |
| `SignaturePackets512` | Флаг-удобство: сигнатуры есть. |

Различение «провод/реал» существует, чтобы операции в режиме секрета всё же могли производить осмысленные отчёты, никогда не печатая ключевое значение (§10).

## 10. Отчёт кодирования

`CodecReport.WriteEncoding(path, stats, fileName)` пишет `<выход>.report.txt` (локализация через `CodecStrings.Language`; одна и та же процедура обслуживает GUI и консоль):

```text
         ════════════════════════════════════════════════════════════════
         DataShield : Отчет по кодированию
         ════════════════════════════════════════════════════════════════
         Имя файла : report.bin
         Размер    : 640 байт
         SHA-256   : 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
         SHA-512   : 2b0c4e…(64 hex)
                    : …(64 hex, выровненное продолжение)
         N (data)  : 10
         M (ECC)   : 1
         Заголовков: 3
         Сигнатурных: 3
         Пакетов   : 17
```

Правила: SHA-512 печатается двумя выровненными строками только при включённых сигнатурах; строка хеша, которой пришлось упасть на проводное значение (реального нет), помечается концевой «*» — при секрете это значение ключевое и простым дайджестом считаться не должно.

## 11. Фазы прогресса

Кодирование отчитывается на глобальной шкале 0..100 в три фазы (имена из `CodecStrings`, троттлинг до целых процентов через `ProgressThrottle`):

| Диапазон | Фаза |
|---|---|
| 0..10 | «Подготовка данных» — хеширование, нарезка на пейлоады |
| 10..75 | «ECC-кодирование» — проход RS (внутри масштабируется `ScaledProgress`) |
| 75..100 | «Формирование пакетов» — построение пакетов по секторам |
| 100 | «Готово» |

Отмена проверяется на тиках фаз; токен доходит и до ядра RS.

## 12. Гигиена памяти и параллельность

- После успешного `Encode` все промежуточные буферы вайпятся: пейлоады данных, ECC-пейлоады и сериализованный заголовок (`Array.Clear`). Остаются только возвращённые пакеты (они и есть продукт) и содержимое вызывающего.
- `StreamEncoder` не держит состояния между операциями (только конфигурация), поэтому параллельные вызовы `Encode` на одном экземпляре безопасны; фасад `DataShieldCodec` дополнительно сериализует всё своим гейтом.
- Самотест хеширования (`VerifySha256`) выполняется перед каждой операцией.
